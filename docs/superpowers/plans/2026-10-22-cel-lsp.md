# Focused CEL LSP Implementation Plan

> **For agentic workers:** Use superpowers:subagent-driven-development. Preserve the existing isolated worktree and uncommitted work; no commits, merges or pushes.

**Goal:** Standardize editor communication on a small real LSP surface without rebuilding CEL semantics.

**Architecture:** One existing CEL engine, one LSP dispatcher, stdio transport for conventional editor clients and loopback HTTP JSON-RPC for the browser. Keep fixture catalog/evaluation separate. Monaco consumes the LSP adapter through existing presentation callbacks. No WebSocket stack or new language engine.

**Tech Stack:** Existing Go CEL tool, TypeScript/Monaco, JSON-RPC 2.0, LSP 3.17.

**Spec:** User-approved conversation design: LSP as a focused authoring adapter, not a resource-query protocol; do not overbuild.

## Global Constraints

- Only isolated resource-intelligence-ui/table-ui; no mainline mutations or auto commits.
- All Go commands GOWORK=off. No client CEL or duplicated semantic engine.
- Scope: initialize/initialized/shutdown/exit, didOpen/didChange/didClose, completion, hover, signatureHelp, pull document diagnostics and cancellation. Advertise only supported capabilities.
- Full document synchronization is sufficient; do not implement incremental edits unless actually needed. Negotiate UTF-8/UTF-16 positions correctly, default UTF-16; preserve Unicode/CRLF behavior.
- Per-client document/version isolation and bounded state. Fixture profile selection is development context, never authority. Host authorization remains outside this development tool.
- Query execution, catalog, builder conversion, mutations and index operations are not LSP requests.
- No formatting, rename, reference indexing, semantic-token engine, generic RPC framework, external editor extension or new dependency unless necessary.
- Runtime JSON validation, structured errors, cancellation, document cleanup and existing limits remain.
